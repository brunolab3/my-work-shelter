# Feature map

Where each part of the game lives, how it behaves and how to QA it. Read the section of what you touch; when you add or change a feature, update its entry here (AGENTS.md only keeps the rules).

## Startup

Startup: `./shelter` or the app `/Applications/work-shelter-public.app` (`./shelter instalar-app` → `scripts/instalar-app.mjs`, icon already prepared in `electron/icono/icono.png`; it opens `./shelter` with `SHELTER_DESDE_APP=1` and places the window itself). Install for people who don't clone: `instalar.sh` (`curl … | bash`: clones into `~/.work-shelter-public`, prepares and creates the app; running it again updates) (Electron + local server on 127.0.0.1:3778, under `server/supervisor.mjs`). Development: `npm run dev` (Vite on :5173 + server under the supervisor); to keep real data untouched, `SHELTER_DATOS=/temp/path` (and `SHELTER_PUERTO`). Identity on disk: `work-shelter-public` (Electron `userData`, `~/Library/Application Support/work-shelter-public`, `~/Library/Logs/work-shelter-public`, keychain service) and port 3778.

## New shelter

New shelter (`shared/refugioInicial.ts`): only the service rooms, no example repos (nothing is cloned; `server/ejemplos.ts` only recognises old example copies so that retiring or relinking such a room still sends the copy to the Trash). The welcome screen (`web/src/ui/Puente.tsx`) asks for the repos root (`raizRepos`, pre-filled with `rootReposDefault()` in `server/estado.ts`: `~/Sites`, `~/Developer`, `~/Projects`…). When the root is chosen (welcome, or changed later in the Vault; `takeRoot()` and `addRoom()` in `server/main.ts`), every git repo directly inside it becomes a room, plus wings (non-git folders with several repos inside, as at the Main Gate: `sugerencias` in `server/repos.ts`); rooms whose folder is outside the new root are retired, except those with someone working and the service rooms. With the root at `~` (or `/`) nothing is added automatically. Non-git folders keep showing as suggestions at the Main Gate. A room is linked to another folder from its panel (action `vincularSala`) or retired. Integrations start `off` (`initialState`; no DEMO data and nothing read, not even Mac Mail/Calendar, GitHub via `gh` or Google via `gws`): entering the shelter opens the Vault to connect them; "forget" turns a source off again (`adaptadores.ts`, `integraciones/index.ts`).

## Game terminals

Game terminals: the PTYs live in `server/anfitrionTerminales.ts` (separate process, Unix socket) and survive server restarts; the client (`web/src/ui/Terminales.tsx`) behaves like iTerm: Esc and Ctrl+C always go to the program, kitty keyboard protocol. Terminals and intercoms are tabbed windows that minimise to the bar and maximise, with the same shortcuts (`web/src/ui/ventanas.tsx`, `Barra.tsx`). Many tabs: they keep a readable width and the strip scrolls; the ⋯ N button (⌘⇧A) lists them all to filter, go and close (one, selected, read or idle, a task's): in a terminal's strip, its tabs; for intercoms, at the end of the bar's COM row, every open intercom conversation by room (`ComTabs` in `Dialogo.tsx`; going to another's switches the intercom to it). Intercom tabs hold that dweller's or hologram's own conversations, most urgent first (`web/src/ui/ordenPestanas.ts`; the active one stays put until you switch away); the selector above the portrait (`WhoSelector` in `Dialogo.tsx`; a chip like the bar's, always the portrait column's width, that opens a fixed-width list like its hover list, each talker with a small bust: dwellers in their colors, holograms tinted with their task's color) switches the intercom to another of the room's dwellers and holograms (most recent conversation first, by the minute then by name; those without one last), each shown with its most urgent conversation's state (coloured like its pilot light, also in the ⋯ N list) and title and how many it has open; closed, it flags the others with something for you (waiting, unread or failed). In the bar, intercoms go one chip per room (`comRooms` in `Barra.tsx`): it opens the one with the most recent conversation and its hover lists one row per open panel (the dweller and each hologram) as the selector does (`roomTalkers`, `TalkerRow`). Lists of conversations by recency (the finder, the logbook, a console's visitors) compare by the minute and then by name (`recentFirst` in `shared/recientes.ts`), so they don't reshuffle while sessions work. Terminal tabs keep their opening order. QA: `scripts/qa-terminal.mjs --reinicio`, `scripts/qa-intercom.mjs`, `scripts/qa-pestanas.mjs` (many tabs), `scripts/qa-barra.mjs` and `scripts/qa-hologramas.mjs --estados/--nacer`, `scripts/qa-copias.mjs` (each holographic copy, with its intercom) (with the real game open, add `&res=0.5` to the URL).

## Going to the surface

Going to the surface (`server/escritorio.ts`, `server/superficie.ts`, `server/controlRemoto.ts`; `remoteName` in `shared/tareas.ts`): conversations and terminals carry on in iTerm, or go to the phone with Remote Control. Details: `docs/superficie.md` (and the Overseer's Manual, F1). QA: `scripts/qa-superficie.mjs`.

## Shelter browsers

Shelter browsers (`web/src/ui/Navegadores.tsx`, `<webview>` in `electron/main.cjs`): one website per window (Linear, in Planning; Outlook, Discord, Slack and GitHub, from the Communications notice board), to use them without leaving the game (integrations still bring the notices), no tabs or address bar, own persisted session (`persist:navegador`), confined to its domain (anything else goes to the system browser); NAV row of the bar. Electron only: changes to `electron/main.cjs` are applied by "restart". Discord and Slack use a Chrome user agent (`chrome: true`: with "Electron/44", Discord thinks it's "Chrome 44"). Gmail has no in-game browser (Google doesn't allow signing in from an embedded Chromium): its notices open in the system browser. QA: `scripts/qa-navegador-webs.cjs` (each site loads without confinement cutting redirects), `scripts/qa-navegador-tablon.mjs <cdp-port>` and `scripts/qa-navegador.mjs <cdp-port>` (Electron with `SHELTER_DEV=1 SHELTER_CDP=<port>` and a temporary `--user-data-dir`). Spotify is not a `<webview>`: see Disco.

## Keyboard

Keyboard: two doors to everything, with its key visible in the top bar. Esc in the shelter opens the game menu (game things only: back, options, F1 shortcuts, restart and «Leave the shelter», whose hatch asks how: stay, go to the surface, everything to your phone or close and stop; `MenuGame` and `Salir` in `web/src/ui/Paneles.tsx`; whatever opens from it returns to it with Esc). ⌘K, from anywhere (also while typing, in a terminal or a browser, which Electron forwards), opens the finder (`web/src/ui/Buscador.tsx`): open and recent conversations of every room (action `conversaciones.recientes`), actions with their key (most used first: "recurring") and, when typing, dwellers and rooms. A new shelter action is added to the finder's `acciones()`. QA: `scripts/qa-buscador.mjs`.

## Mouse in the shelter

Mouse in the shelter (`web/src/mundo/refugio.ts`, `apuntar()`): hovering a dweller, a copy, a device or the elevator shows its label with "Click", and a click uses it at once (opens its panel or the chat) while the Overseer walks there; whatever is in front wins. Each room marks the visible parts of its devices with `ctx.aparato(id, pieza)` (boxes measured before merging the static geometry, in `Interactive.zones`); unmeasured, the column behind its point counts. Dragging moves the camera (`ShelterCamera.desplazamiento`), which returns to the framing as soon as the Overseer walks. QA: `scripts/qa-apuntar.mjs`.

## Tasks and worktrees

Tasks and worktrees: talking to a room's dweller works in its main copy; worktrees belong to tasks (organise the room by tasks, `server/organizar.ts`, and the Logistics split). Each Jira task (and PR) has a color (`shared/tareas.ts`, assigned and saved by `server/coloresTareas.ts`; in the client, `web/src/ui/tareas.ts`) shown on the boards, the screens, the hologram of its copy (body, projector disc, label) and its bust in the intercom and the bar; slug tasks and worktrees without a task all share the holograms' cyan, `NO_TASK_COLOR`, outside the palette (`hasTaskColor`), and take no assignment; the copy's name (label, bar, intercom, finder) adds the task's title when the Jira board has read it (`copyCaption` in `web/src/ui/copias.ts`). One task, one worktree: creating a second one for a task that has one (`git worktree add`, `EnterWorktree`) is denied with the existing path (`oneWorktree` in `server/sesiones.ts`, `taskWorktreeIn` in `shared/tareas.ts`). Task keys are Jira keys (ABC-123) or, outside Jira, descriptive slugs (`preflight-popover`), both matched exactly (`taskKey`, `worktreeHasTask` in `shared/tareas.ts`). Worktrees come from `send_to_room` with a task key, which creates one and opens a session in it: `git worktree add` from a session outside any worktree (a room's main copy) is denied (`handMadeWorktree` in `shared/tareas.ts`); `EnterWorktree` stays allowed, since it moves the session itself. `gh pr create` or `gh issue create` aimed at the original repo (`-R`, a remote, or a fork's parent) asks the user first, since nobody reads them there (`originalRepoGate` in `server/sesiones.ts`, `ghCreateOf` in `shared/tareas.ts`).

## Logistics

Logistics (room `tareas`, `PLANNING_ROOM` in `shared/disposicion.ts`): plans a Jira task with every repo in view and splits it across rooms with in-process MCP tools (`server/reparto.ts`), with a versioned shared plan (`server/planes.ts`) and the messenger robot (`web/src/mundo/mensajero.ts`). Planning is the Jira board (`cruzarTablero` in `shared/tablero.ts`). Details: `docs/integraciones-uso.md` ("Logistics, tasks and PRs").

## Messages between rooms

Messages between rooms (`server/avisosSalas.ts`, MCP `salas` in every conversation): `send_to_room` to any room's dweller, with or without a task key; inside the same room the dweller hands it to the task's hologram (`enMano` in `web/src/mundo/mensajero.ts`). With a `thread` slug instead of a key, to that thread's open conversation in the room's main copy (queued if busy; a new one takes over once it closes, and never the sender's own), tracked per room and thread in memory: "Restart the game" closes every conversation anyway. Conversations in a worktree also get `request_worktree_cleanup`: the game writes the cleanup request from the session's cwd (worktree, branch, merge into `local` if the repo has that branch) and sends it through the own room's `cleanup` thread, one cleanup at a time. Details: `docs/integraciones-uso.md` ("Logistics, tasks and PRs").

## Reviews of your PRs

Reviews of your PRs (`server/revisionesPR.ts`, every minute with GitHub connected): what others write on your open PRs goes to the conversation in the PR's worktree. Details: `docs/integraciones-uso.md` ("Logistics, tasks and PRs").

## CI failures of your PRs

CI failures of your PRs (`server/fallosCI.ts`, every minute): a failing check on a PR's head goes once to the same conversation as reviews. Details: `docs/integraciones-uso.md` ("Logistics, tasks and PRs").

## Finished tasks

Finished tasks (`server/limpiezaTareas.ts`, every 5 minutes with GitHub connected): when all PRs of a task in a room's repo are merged or closed, the game removes its worktrees and local branches by itself if git shows nothing left (uncommitted changes to tracked files, stash of its branch, commits not on the remote nor on the PR's head; untracked files don't count and go to the macOS Trash); with an open conversation it waits; with work left it asks the Overseer once with a notice that stays until answered (`NoticeQuestion`, action `aviso.responder`) before forcing it (a yes while a conversation is open in it removes it as soon as that conversation closes). A worktree removed some other way (by hand, or by a session after merging) takes its conversations with it: `orphanedConversations` closes them in the minute sweep of `server/main.ts` once idle, read and not in use in the intercom (`enUso`); until then its hologram stays with them (the client's fallback for a session's fresh worktree in `web/src/mundo/hologramas.ts`). QA: unit test in `server/limpiezaTareas.test.ts`.

## Deployment plan

Deployment plan (`web/src/ui/Despliegue.tsx`, `shared/despliegue.ts`, Logistics' big screen in `web/src/mundo/salas/despliegue.ts`; manual blockers in `server/bloqueosPR.ts`). Details: `docs/integraciones-uso.md` ("Logistics, tasks and PRs").

## Pre-flight of a task

Pre-flight of a task (`web/src/ui/Preflight.tsx`, model `shared/preflight.ts`, `server/preflight.ts`): whether each PR of a Jira task, across rooms, is ready to merge (state, CI, review, conflicts, blockers; a click opens the PR), in a small floating box over whatever is open (not a panel: Esc or a click outside closes it and nothing underneath changes), also for tasks already fully merged; offered (intercom ✈, ⌘K, F on the selected card of the deploy board and of the Jira board) only for tasks with a PR (`taskHasPRs`), plus the ask-first gate on `git push` (`pushGate` in `server/sesiones.ts`) with compare and checklist, which the window doesn't show. Details: `docs/integraciones-uso.md` ("Pre-flight of a task"). QA: `scripts/qa-preflight.mjs`.

## Usage per conversation

Usage per conversation: the session summary carries `tokens` and `contexto` (`shared/protocolo.ts`); `Usage` in `web/src/ui/consumo.tsx` shows it in the intercom and in the room card (`RoomCard` in `web/src/ui/Paneles.tsx`). In the intercom's status line, an idle conversation (`compactNeed`) shows «Compact» from 60 % of the window, pulsing from 85 % (near Claude Code's auto-compact): it sends `/compact` as a message, and the `compact_boundary` that follows logs it and measures the context again (`server/sesiones.ts`).

## Links in replies

Links in replies (`web/src/ui/markdown.ts`): web links open outside; those pointing at a file on the Mac (`/Users/…`, `~/…`, `file://…`, and the temporary folders `/tmp`, `/private/tmp`, `/var/folders`) are opened by the server without running anything (action `enlace.local`, `openLink` in `server/paginasLocales.ts` and `openLocal` in `server/abrir.ts`: HTML pages (plans, reports, compares) and Markdown files (rendered to HTML by the server, mermaid blocks drawn) inside the game, in the «Página» window of `Navegadores.tsx`: served at `/pagina/<key>/…` with a random key per folder, a `sandbox` CSP header and a sandboxed `<iframe>`, no data requests (`connect-src 'none'`; only scripts, styles and fonts from the public CDNs jsdelivr, unpkg and cdnjs, which the dwellers' pages use for marked or mermaid); the Overseer leaves notes on them (select → «✎ Note», `server/pagina/notas.js` injected in each page, saved per file in the client, `pageNotes`) and sends them inline to the conversation that linked the page (every conversation has the `compare_changes` tool, `server/comparar.ts`: its branch vs. its base as such a page, or another worktree of the same repo with `carpeta`, in the game's `.data/compares`, to review with notes before a push); in compares, «+» on a line leaves a note on that line, as on GitHub); each intercom conversation lists the pages it linked («📄 Pages», under the dweller's portrait; `PagesMenu` in `Dialogo.tsx`, `shared/paginasSesion.ts`): only those linked in the last 14 days that still exist (action `paginas.existen`: a removed worktree's pages disappear; compares go once their worktrees are removed, or after 14 days, `cleanCompares`), pending until notes are sent or it is validated («✓ Validate»), ✕ drops one from the list (it comes back if linked again), 📁 shows it in Finder to share it (action `enlace.revelar`); the «Página» window opens on the left, full height, beside the intercom on the right (a maximized intercom steps back to the right; opening an intercom un-maximizes the page window and minimizes other maximized browsers); an intercom opened while another is on screen takes its maximized state, otherwise it opens on the right, never restoring an old maximized state; a page opened without its conversation sends its notes to the last one that linked it; links to pages another local program serves (`http://127.0.0.1:<port>`, `localhost`, e.g. a review page with notes) open in that same window, and «Send notes» tells the conversation that linked it to apply them; images (png, jpg, gif, webp, avif, bmp, svg; `IMAGE_FILE` in `shared/paginasSesion.ts`) also in the «Página» window, drawn by the game with a key for that file only, and each one a reply links or embeds (`![](…)`) shows a bounded thumbnail after it that opens it there (`withThumbnails` in `markdown.ts`, action `enlace.miniatura`; QA: `scripts/qa-imagenes.mjs`); HEIC, TIFF and PDF in Preview, code in the editor, folders in Finder and anything else only revealed in Finder).

## Intercom

Intercom: attachments (paste, drag, 📎/⌘U; `server/adjuntos.ts`: images go inside the message, shrunk with `sips`) and dictation (🎙/⌘D; `server/voz.ts` compiles `server/voz/transcriptor.swift`, macOS 26 dictation on the Mac itself: no network and no inference by the shelter). Client in `web/src/ui/entrada.tsx`. QA: `npx tsx scripts/qa-voz.ts` and `scripts/qa-adjuntos-voz.mjs` (fake microphone, real session with Haiku). macOS notifications: a conversation that starts waiting for your answer (question, permission or plan) while the game isn't in front shows one; clicking it brings the game with that conversation open, answering removes it (`web/src/ui/avisosSistema.ts`, `avisosPendientes.ts`; given by Electron, `aviso` in `electron/main.cjs`; none after going to the surface). A main-agent `AskUserQuestion` with no text written to the user earlier in the turn is denied once per turn, asking for the full message (results, links) first, so the answer comes with everything in view; the retry goes through (`canUse` in `server/sesiones.ts`; test `server/preguntaSinTexto.test.ts`). Dock badge: the number of requests waiting for your answer, or a dot while a conversation finished its turn unread (`dockBadge`, `insignia` in `electron/main.cjs`); board notices don't count. What you type is never lost (tabs, text and attachments saved in the page; conversations in view or with something typed never close by themselves, `enUso`); QA: `scripts/qa-borradores.mjs` (also ⌘C).

## Version Control

Version Control (room `git`, floor -2): git client for every repo in the shelter (`web/src/ui/git/`, `server/git.ts`, actions `git.*`; staging by files, hunks or lines with `git apply --recount`), contribution matrix and GitHub PRs with `gh`, and the Octocat (community CC-BY model in `assets/terceros/octocat/`, versioned in the repo, without a KayKit skeleton: animated by code in `web/src/mundo/octocat.ts`; QA: `scripts/qa-octocat.mjs`). G opens it. QA: `scripts/qa-git.mjs` with a test shelter and test repo (it commits in it).

## Files

Files (only through the ▤ Files button of the git client, deliberately without a key or finder action: it's for touching something now and then): explorer and editor for the rooms' folders and their worktrees, with Cursor's keys (`web/src/ui/archivos/`, `server/archivos.ts`, actions `archivos.*`). The editor is Monaco (VS Code's), loaded separately the first time (`archivos/monaco.ts`, its workers via `?worker`); the tree dims what git ignores and colors what changed; ⌘P also finds loose files git ignores (.env files); saving never overwrites changes on disk without asking, and untouched files reload by themselves. Deleting sends to the macOS Trash. Only inside the shelter's roots (no `..` or links leading out). QA: `scripts/qa-archivos.mjs` with a test shelter and test repo.

## Disco

Disco (leisure floor, between the crops and the elevator): Spotify plays in a windowless Google Chrome (`electron/chromeRemoto.cjs`: `--headless=new`, own persistent profile in `Application Support/work-shelter-public/chrome-spotify`, which the first time inherits Spotify's cookies from `persist:navegador`). Reason: Spotify protects audio with Widevine and its licence server only grants licences with a production VMP signature, which Chrome has and Electron doesn't. The game's Spotify browser (`remoto` in `Navegadores.tsx`, `RemoteView`) shows its page by screencast and forwards mouse, wheel and keyboard (invisible field: accents and ñ) over IPC (`electron/precarga.cjs`: `window.shelterRemoto`); outside links go to the system browser; "Continue with Google" opens in a visible Chrome with a temporary profile (`electron/loginChrome.cjs`: Google rejects login in any embedded Chromium and in a Chrome with `navigator.webdriver`). Input is queued without piling up stale events (only the last mouse move; wheel turns summed): a click arrives in ~40 ms even while the mouse moves; the image comes at the screen's density (Chrome starts with `--force-device-scale-factor`). The deck (`web/src/ui/Discoteca.tsx`), bottom left above the window bar (`.columna-izquierda`), compact (record, track and artist) and expanded on hover or with ⌘J (J in the shelter; Space, ←→ ±10 s, ⇧←→ tracks, ↑↓ volume, Enter opens Spotify, Esc leaves), drives it through `window.__refugioMusica` (`electron/mandoMusica.js`, injected in the page; seeking moves Spotify's progress bar, which doesn't register "seekto"). Closing the window closes Chrome (and the music). QA: `scripts/qa-spotify-chrome.cjs` (test game, no account) and `scripts/qa-discoteca.mjs <cdp-port>` (Electron with `SHELTER_CDP` and a temporary `--user-data-dir`; fakes the Media Session).

## Characters from parts and the Body Shop

Characters from parts and the Body Shop (leisure room, key P): every character (except the Octocat, which is what it is) is a look (`shared/aspecto.ts`: human or robot, parts and colors; the server validates it, action `aspecto.guardar`) assembled on the KayKit skeleton from parts of its 63 characters (`web/src/mundo/figura/`: `despiece.ts` splits heads and clothes by atlas bands, `ajustes.ts` the hand-tuned fixes, `horma.ts` the shape of each head (hair, beard, eyebrows, hats and glasses adapt to the chosen face, hair tucks under the hat and the filler skull comes from the face itself), `montaje.ts` binds and paints by regions, `estudio.ts` the fitting-room view and thumbnails). ## Set dressings

Set dressings ("Adapt the room to the repo", room panel or ⌘K): the dweller of a repo room designs it a scene with the game's tools, an in-process MCP server that only touches THEIR room (`server/decoradoSala.ts`: guide, prop catalogue measured from the glTFs (`server/atrezo.ts`), apply, photo with `server/capturaSala.ts` and remove; they don't ask for permission). The dressing is data, never code: `shared/decorado.ts` validates and reviews it (server on receiving it and on loading the state), it's saved in the room (`decorado`) and the client builds it in `web/src/mundo/salas/decorado.ts` on top of a stock scene or the empty room. Without a dressing, the scene comes from the repo's style or type (`baseStock`). Guide: `docs/decorados.md`. QA: `scripts/qa-decorado.mjs` (real session; test shelter).

## Other agents as dwellers

Other agents as dwellers (Codex): today only Claude Code (`server/sesiones.ts`, Agent SDK); the guide for asking for it is in the README ("What about Codex?"). If asked: inventory and a phased plan before touching anything; Claude Code stays the same; the agent is chosen per room; with the user's own session (zero inference of its own: no API keys); permissions through the game's dialog (`web/src/ui/Dialogo.tsx`). What assumes Claude Code outside `sesiones.ts`: resuming outside (`server/superficie.ts`, `server/escritorio.ts`), visitors (`projectFolder` in `server/repos.ts`, `web/src/mundo/visitantes.ts`), project trust, set dressings (in-process MCP, `server/decoradoSala.ts`), Logistics (`server/reparto.ts`), terminals (`server/terminales.ts`) and Linear (`server/integraciones/linear.ts`).

## Always up to date, without asking the Overseer for anything

Always up to date, without asking the Overseer for anything (`scripts/huellas.cjs`, content fingerprints of client, server and app): "restart" rebuilds the client if its fingerprint doesn't match the last build's and, if `electron/`, the supervisor or `./shelter` changed, exits with code 76 and the app reopens entirely (terminals alive). An app opened with an Electron other than the one in `node_modules` reinstalls itself (`instalar-app.mjs`) and reopens. Opening the app clears the game's HTTP cache and, if an older server is still running, brings it up to date (`/poner-al-dia`). The server serves assets with ETag and `no-cache` (only hashed builds are immutable). Never ask the Overseer to clear caches, reopen or reinstall the app to see changes: if something doesn't update by itself, fix it in the game.
